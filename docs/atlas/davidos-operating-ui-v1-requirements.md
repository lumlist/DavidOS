## Executive Recommendation

The v1 operating UI is not a custom UI. It is a thin, opinionated configuration of three already-running surfaces with one new view layer:

1. **Paperclip** — primary control plane. Agents, projects, issues, runs, work products, activity, documents, costs.
2. **Obsidian-MCP over the DavidOS git repo** — David's read/write cognition surface for prose memory (`raw / wiki / output / archive`). The vault is a synced view on the repo, not a separate store.
3. **Langfuse (self-hosted)** — observability of every agent run, tool call, routing decision, and budget event.
4. **One thin custom add-on: a "Daily Operating View"** — a single-page, mostly-read-only briefing assembled from Paperclip + repo + Langfuse via APIs. This is the only piece that does not exist today.

This is a deliberate anti-overengineering choice. Per the Atlas Operating Spec and DAV-15 §9, premature custom UI is the most common failure mode for AI workspace projects. v1 spends ~90% of its UI budget on configuring and integrating what we already have, and ~10% on a single custom view that materially improves David's daily input quality and observability.

Future customer-facing iZZi AI Systems reuse: the same three-surface pattern (control plane + curated cognition surface + observability) plus the Daily Operating View becomes a **productized customer template** distributed via ClipHub. The customer-facing product is the diagnostic + buildout service that produces this template for them — the UI is a deliverable, not the product (DAV-15 §9).

Three specific commitments this memo asks David to make:

- (a) Adopt Paperclip + Obsidian-MCP + Langfuse as the v1 stack. No new UI framework, no new dashboard tool, no admin panel build.
- (b) Approve the `raw / wiki / output / archive` folder layout under `docs/` with a curation gate for `wiki/` and `archive/` promotion.
- (c) Approve a thin "Daily Operating View" — single HTML page or Obsidian dashboard note, generated by a script — as the only custom UI element built in v1.

## 1. Product Purpose

The v1 UI exists to do five things, in priority order:

1. **Improve input quality** — make it easy for David to give Atlas and project-lead agents structured, high-signal context (goals, constraints, deadlines, decisions, evidence) instead of free-text drift.
2. **Increase observability** — make the state of every active task, project, agent, and the system itself legible at a glance, with one click to deeper detail.
3. **Surface decisions and approvals** — make pending approval gates and open decisions impossible to miss; make approval an explicit, separate gesture (not a continuation of an agent turn).
4. **Support memory hygiene** — make it easy to read, edit, and curate durable knowledge in the repo, and easy to see what's `raw` vs `wiki` vs `output` vs `archive`.
5. **Stay out of the way** — the UI must add zero noise. If a feature does not directly serve one of the four above, it does not ship in v1.

Non-goals for v1:

- Customer-facing product UI.
- Real-time streaming agent output (Paperclip's activity log is sufficient).
- Custom chat UI (Paperclip issue threads + Obsidian + Hermes terminal are sufficient).
- Mobile app.
- Per-customer multi-tenant features.
- Embedded analytics / BI dashboards.

## 2. User Modes

Two modes in v1. Both run on the same underlying stack; they differ only in which surfaces are foregrounded and which approval thresholds apply.

### 2.1 David Mode (now)

Single operator. Approval required for: code changes, commits/pushes, installs, paid services, credentials, production systems, irreversible changes, sensitive personal data, new agent creation. Approvals are explicit gestures in Paperclip (issue comment with structured directive) or in the terminal (Hermes prompt response) — never implicit continuation of an agent turn.

Surfaces, in order of typical use:
1. Daily Operating View (single page) — start of session.
2. Paperclip board / issue thread — pick up work, comment, assign, approve.
3. Obsidian-MCP over `docs/` — read/write durable memory.
4. Hermes terminal / Atlas chat — strategic conversation.
5. Langfuse trace UI — only when investigating cost or quality anomalies.

### 2.2 Future iZZi Customer Mode (deferred, but designed for now)

Same architecture, different policies. The customer is the operator; their analog of Atlas is a customer-Lead agent. Approval gates are configurable per customer. The Daily Operating View, the `raw/wiki/output/archive` repo pattern, and the three-surface stack ship as a ClipHub template (DAV-15 §9, doc/CLIPHUB.md).

What carries over from David Mode: the entire architecture. What changes: branding, customer-specific domains, default agent roster, observability cost ceilings, and approval-gate strictness.

The implication for v1 design: every screen, schema, and workflow built for David Mode must be implementable as a parameterized template. Concretely, that means:

- No David-specific strings hard-coded in any UI element. Use config keys (`operator_name`, `company_name`, `domains[]`).
- All folder paths, agent IDs, and policy constants live in one config file, not scattered across docs.
- Every approval-gate type is a labeled category (e.g. `approval_kind: install`, `approval_kind: paid_service`) so the customer template can map them to that customer's policy.

## 3. Core Screens

Five screens. Three exist today (Paperclip), one is a new minimal view, one is configuration.

### 3.1 Paperclip Board (exists)

The primary daily surface. Already provides: issues by status × priority × assignee, project filter, agent filter, label filter, run/checkout state, blocker attention, document attachments, comment threads, activity log.

Required v1 configuration changes:

- Default board filter: `assignee=Atlas OR assignee=David, status in [todo, in_progress, blocked]`.
- Pin the four active projects (DavidOS, FamilyAI, DavidAIStory, AI Workspace Diagnostic Service) at the top.
- Enforce a small label set: `approval-needed`, `decision-needed`, `experiment`, `automation-candidate`, `customer-pattern`. No free-form labels in v1.
- One additional comment-template button: "Approve" (posts `[APPROVAL: <approval_kind>] <free text>` so heartbeat logic can detect it without parsing prose).

### 3.2 Paperclip Issue Thread (exists)

Already provides: description, comments, work products, document attachments (`memo`, `plan`, etc.), referenced issues, blocker graph, run history.

Required v1 configuration changes:

- Convention: every substantive Atlas output attaches as a document at a stable key (`memo`, `plan`, `review`) — not buried in comment prose. (Already the pattern on DAV-15; codify.)
- Convention: every comment posted by Atlas tags its purpose at the top: `[STATUS]`, `[QUESTION]`, `[RECOMMENDATION]`, `[BLOCKER]`, `[DELIVERABLE]`. Lets David scan threads in seconds.
- Convention: when an approval is needed, Atlas posts a `[APPROVAL-REQUEST]` comment with a structured block (what / why / risk / reversibility / expected cost). David replies with `[APPROVAL: <kind>]` or `[REJECT]`. No approvals inferred from prose.

### 3.3 Daily Operating View (new — the only custom UI in v1)

A single static HTML page, regenerated on demand or every N minutes by a script (`scripts/render-daily-view.py` or similar). Pulls data from Paperclip API + repo file mtimes + Langfuse API. No interactive backend; all interactivity happens by clicking through to Paperclip / Obsidian / Langfuse.

Sections, in this order on the page:

1. **Top of mind** — David-authored, edited in Obsidian (`docs/daily/today.md`). 3-5 bullets, max.
2. **Active issues** — table from Paperclip board: identifier, project, assignee, status, priority, last activity, "next action."
3. **Pending approvals** — every comment matching `[APPROVAL-REQUEST]` without a paired `[APPROVAL]` / `[REJECT]`. Click → Paperclip thread.
4. **Open decisions** — every issue with label `decision-needed`. Same shape.
5. **Recent deliverables** — last N work-product/document attachments across all issues, ordered by time.
6. **System health** — three numbers: agent runs in the last 24h, total cost in the last 24h (from Langfuse), heartbeat-loop status (boolean derived from "any agent issue reopened from done/cancelled in the last 24h"). Each number links to its Langfuse / Paperclip detail view.
7. **Memory freshness** — list of `wiki/` files not edited in 60+ days, and `raw/` files not promoted in 14+ days. Surfaces curation debt.
8. **Atlas recommendations** — a single section Atlas writes to (markdown file, e.g. `docs/atlas/recommendations-today.md`) when it has a non-urgent suggestion. Capped at 5 items; Atlas evicts the oldest before adding a new one.

The page is generated, not interactive. This is intentional — it forces David to act in Paperclip / Obsidian / terminal, where actions are durably logged. No state lives in the Daily Operating View itself.

### 3.4 Obsidian View Layer over `docs/` (new — configuration only)

Install Obsidian-MCP server (https://github.com/cyanheads/obsidian-mcp-server) pointed at `/home/hermes/projects/personal-ai-workspace/docs/`. The Obsidian vault IS the `docs/` folder; git is the audit log.

Required v1 configuration:

- Obsidian core plugins: Daily Notes, Templates, Outliner, Tag Pane.
- One community plugin only: Smart Connections (semantic search). No Dataview, no Tasks, no Calendar in v1 — they pollute the vault with plugin-specific syntax that's hostile to the repo-as-truth model.
- Templates folder with three templates: `daily-note.md`, `decision-memo.md`, `deep-dive-output.md` (mirrors the Domain Deep Dive Skill output spec).
- One workspace layout saved: left pane = file tree, center = current note, right pane = backlinks + Smart Connections.

Curation gates implemented as folder-permission convention (not enforced by software in v1):

- `raw/`, `output/`, `docs/atlas/runs/` — agents may write freely.
- `wiki/`, `archive/` — agents may propose changes via PR or `[PROMOTION-REQUEST]` comment; David approves.

### 3.5 Langfuse Trace View (new — installation only, default UI is fine)

Self-hosted Langfuse on the same host. Used reactively, not as a default surface. Embedded as deep links in:
- The Daily Operating View "system health" section.
- Atlas-posted `[STATUS]` comments on any run that exceeded a threshold (cost > $X, turns > N, escalations > 0).

No dashboards customized in v1. Langfuse default UI is sufficient.

## 4. Guided Input Model

David's #1 pain point is that free-form input produces low-signal context. v1 fixes this with three patterns:

### 4.1 Issue templates (in Paperclip)

Three structured templates, accessible from the "New Issue" button via a label preselect:

- **Decision request** — fields: decision; options considered; constraints; deadline; what would change my mind; current best guess.
- **Domain Deep Dive request** — the input schema from `domain-deep-dive-skill-v0.md` §"Input Schema," verbatim, as a checkboxed description template.
- **Build request** — fields: outcome; smallest viable scope; out-of-scope; success criteria; risk class (reversible / irreversible); approval gates anticipated.

The templates are simply pre-filled markdown blocks Paperclip drops into the issue description — no schema enforcement at the API level in v1.

### 4.2 Daily Note (in Obsidian)

`docs/daily/YYYY-MM-DD.md` with template:

```
## Top of mind
- 

## Decisions I want made today
- 

## Things I'm waiting on
- 

## What I learned yesterday
- 

## Cost / energy check (1-5)
- 
```

The Daily Operating View reads from this file. The template forces David into structured-but-low-effort input.

### 4.3 Atlas-led intake conversation (in Hermes terminal / Paperclip thread)

For any new project or major decision, Atlas opens with a fixed intake script:

1. What outcome are you trying to achieve?
2. By when?
3. What's already been tried or decided?
4. What's the risk class — reversible or irreversible?
5. Who else is affected?
6. What would change your mind?

Atlas writes the answers into a Decision Memo using the Domain Deep Dive output template (12 sections from `domain-deep-dive-skill-v0.md`). This memo becomes the document attachment on the issue.

## 5. Observability Model

Implements the four levels from `agentic-os-video-evaluation-v0.md` §"Observability Requirements." Every level maps to a concrete data source and a concrete surface.

| Level | Data source | Where David sees it |
|---|---|---|
| Task | Paperclip issue + run + execution_lock fields; Langfuse spans for the run | Issue thread (live); Daily Operating View "active issues" table |
| Project | Paperclip project + issue rollups; project lead role assignment | Paperclip project page (filter board by project); Daily Operating View "active issues" grouped by project |
| Org / Agent | Paperclip agent registry + assignment counts + cost-by-agent (from Langfuse) | Paperclip agent detail page; Daily Operating View "system health" |
| System | Langfuse traces; heartbeat-loop signal; memory-freshness signal; cost trend | Daily Operating View "system health"; Langfuse default dashboard |

OpenTelemetry GenAI Semantic Conventions are mandatory for all instrumentation per DAV-15 §6 / §13. Concretely: every Hermes/Atlas run emits OTel spans for each (a) routing decision, (b) MCP tool call, (c) model call, (d) approval gate, (e) budget event. Langfuse ingests these.

Three observability rules promoted to durable policy:

- **No invisible action** — every agent action emits a span. If a tool call doesn't emit a span, the tool is not allowed in production.
- **Cost is observable per run, per session, per day** — Langfuse cost rollups visible at all three time scales.
- **Heartbeat-loop detection is automated** — a daily script checks for issues reopened from `done`/`cancelled` to `todo` within 1h. Any hit fires an `[ALERT]` comment on a system-health issue and surfaces in the Daily Operating View.

## 6. Memory Interaction Model

Codifies the DAV-15 §4 / §5 hybrid recommendation into concrete UI behavior.

### 6.1 Repo as source of truth

`/home/hermes/projects/personal-ai-workspace/docs/` is the single source of truth for prose memory. Git is the audit log. No prose memory lives in Paperclip DB; no prose memory lives in Obsidian vault metadata; no prose memory lives in agent context windows.

Folder layout (proposed under `docs/`, requires David approval to actually create — the issue forbids file-modification commits without approval):

```
docs/
  raw/             # transcripts, screenshots, agent-output dumps, web-extract pastes
  wiki/            # cleaned, durable concepts and reference knowledge
  output/          # final memos, decision records, deliverables
  archive/         # superseded material
  daily/           # daily notes (template-driven)
  atlas/           # Atlas operating spec, runs, skills, policies (existing folder)
```

`docs/atlas/` stays as it is — it's already structured and is Atlas's working memory of itself.

### 6.2 Curation gates

| Folder | Agents may write directly? | Promotion path |
|---|---|---|
| raw/ | Yes | Agents propose `wiki/` promotion via `[PROMOTION-REQUEST]` comment; David approves; agent moves the file. |
| output/ | Yes (only when explicitly producing a deliverable for an issue) | Promotion to `archive/` is automatic after the issue closes + 90 days. |
| wiki/ | No, except via approved promotion | Edits require David approval. |
| archive/ | No | Read-only. |
| daily/ | David writes; Atlas may append `[ATLAS-NOTE]` blocks | Auto-archived after 90 days. |
| atlas/ | Atlas writes (this is the system's self-knowledge) | Versioned via filename suffix (`-v0`, `-v1`) — no overwrites. |

### 6.3 Obsidian as view layer

Obsidian-MCP server reads and writes the same files. David's edit gestures (rename, link, refactor) propagate to git via vault save → manual or scheduled `git commit`. No automatic commit in v1 — every commit is a deliberate human gesture.

Smart Connections plugin provides semantic search over the vault. Vector-DB-as-memory (LanceDB etc.) is deferred per DAV-15 §11 until corpus exceeds ~50K notes.

### 6.4 Memory freshness signal

Daily Operating View surfaces:
- `wiki/` files unchanged in 60+ days (potentially stale durable knowledge).
- `raw/` files older than 14 days never promoted (curation debt).
- Top 10 most-linked `wiki/` files (probable hubs that deserve attention).

## 7. Decision / Approval Model

Implements the approval-gate principles from `atlas-operating-spec.md` §"Autonomy Model" + DAV-15 §10 (rule: "explicit human approval as a separate gesture, not a continuation of the agent turn").

### 7.1 Approval kinds (the only ones in v1)

| Kind | Examples | Default policy |
|---|---|---|
| `code-change` | repo file edits, commits, pushes | Always require approval |
| `install` | tool install, MCP server install, dependency add | Always require approval |
| `paid-service` | new SaaS, model upgrade with cost impact | Always require approval |
| `credential` | API key handling, secrets | Always require approval |
| `production` | Vercel deploy, Supabase migration, customer-facing change | Always require approval |
| `irreversible` | deletes, data migrations, account creation | Always require approval |
| `new-agent` | creating a new agent in Paperclip | Always require approval |
| `policy-change` | edit to `docs/atlas/*-policy.md`, governance rule, routing default | Always require approval |
| `wiki-promotion` | move from `raw/` to `wiki/` | Always require approval |
| `archive-promotion` | move to `archive/` | Approval required if the source file is `wiki/` |
| `safe-doc-edit` | edits within `docs/atlas/runs/`, `docs/daily/`, `raw/` | Pre-approved (no per-action approval) |

### 7.2 Approval workflow

1. Atlas detects approval is needed.
2. Atlas posts `[APPROVAL-REQUEST]` comment on the relevant issue with structured block: `kind`, `what`, `why`, `risk`, `reversibility`, `expected_cost`, `proposed_action`.
3. The comment surfaces in the Daily Operating View "pending approvals" section.
4. David replies with `[APPROVAL: <kind>]` or `[REJECT]` (single comment, no prose required).
5. Atlas executes the action only after detecting the matching approval comment. Approval is **not** inferred from continuation of the agent turn or from passive non-objection.
6. Every approval is logged as a Langfuse event with `approval.kind`, `approval.granted_by`, `approval.granted_at`.

### 7.3 Decision records

For decisions (not approvals), the unit is a Decision Memo attached as a document on an issue with key `decision`. Template fields: decision, context, options considered, evidence, recommendation, decision made, by whom, date, revisit-on date. Every `decision-needed`-labeled issue must produce a `decision` document before it closes.

## 8. Integration With Paperclip, DavidOS, Obsidian, Hermes, Atlas

The integration story across the v1 stack. Each pair gets one paragraph; constraints and interfaces are explicit.

### 8.1 Paperclip ↔ DavidOS repo

Paperclip's project workspace already points at `/home/hermes/projects/personal-ai-workspace` (verified on DAV-16 project record). All Paperclip-issued runs operate in this `cwd`. Convention: deliverables produced by a run are committed (after approval) to `docs/output/<issue-id>-<slug>.md` and attached as a document on the issue at a stable key. Paperclip is the operational state store; the repo is the prose store.

### 8.2 Paperclip ↔ Obsidian

Indirect: both read/write the same `docs/` files. Paperclip writes via agent runs; Obsidian writes via David's editor. Conflict resolution = git (rare in single-operator mode; if a conflict happens, the agent run loses, since David's intent is always authoritative).

### 8.3 Obsidian ↔ Hermes / Atlas

Hermes already runs in the repo. Atlas in agent runs has direct file access. Obsidian-MCP gives David's interactive Atlas chat session (when used in environments that support MCP) the same vault as a tool surface. The crucial integration: when Atlas writes a deliverable, it writes to the file system; David sees it appear in Obsidian with no sync step.

### 8.4 Hermes ↔ Paperclip

Already integrated — Hermes is the runtime for the Atlas agent in Paperclip's `local_trusted` deployment mode. The integration that matters for the UI: every `[STATUS]` comment Atlas posts must include the Hermes session ID (already done in DAV-15 / DAV-1 heartbeat comments) so traces are correlatable end-to-end.

### 8.5 Atlas ↔ everything

Atlas is the only required interpreter of the operating spec, tool-selection policy, and the `raw/wiki/output/archive` curation gates. Atlas may be embodied in different runtimes (Hermes today, possibly Claude Code or another runtime later per DAV-15 §13), but the operating spec and policies travel with the role, not the runtime. The v1 UI's job is to make the operating spec legible to David in real time — every Atlas decision visible in the Daily Operating View must trace back to a specific clause in the operating spec or policy file.

### 8.6 Langfuse ↔ everything

One-directional: every component emits OTel spans into Langfuse. Langfuse never writes back. The only thing the UI does with Langfuse is read (cost rollups, trace links, run timelines).

## 9. What Not to Build Yet

Promoting clarity here because the temptation to over-build a v1 UI is the primary failure mode (DAV-15 §9, `atlas-operating-spec.md` §"Anti-Overengineering Rule"). Each item below has a deferred-until trigger.

| Don't build in v1 | Defer until |
|---|---|
| Custom React/Next.js dashboard | 60+ days of v1 usage data identifies a workflow gap Paperclip + Obsidian + Daily Operating View can't fill. |
| Real-time agent activity stream UI | A specific scenario emerges where post-hoc Paperclip activity log is provably insufficient. |
| Custom chat UI | Hermes terminal + Paperclip threads stop being good enough. |
| LanceDB / vector retrieval over the vault | Corpus exceeds ~50K notes (DAV-15 §11). |
| Multi-tenant customer onboarding flow | First paying iZZi customer is identified and has signed an LOI. |
| Cost-budgeting controls beyond Langfuse rollups | Spending exceeds $X/month consistently (David sets X). |
| Custom approval-gate UI | `[APPROVAL-REQUEST]` / `[APPROVAL]` comment convention proves insufficient over 30+ approval gestures. |
| Project-lead agent UIs | The next agent (FamilyAI Lead per DAV-15 §8) is created AND its workload exceeds Atlas's capacity to context-switch. |
| Notifications / push / mobile | David asks for it after experiencing the friction directly. |
| Customer-facing iZZi product UI | A diagnostic engagement is signed and the customer's repo is provisioned. |

## 10. Immediate Build Plan

Sequenced, each item with effort estimate, approval gate, and stop-condition. Items marked "approval gate" require David's `[APPROVAL]` before Atlas executes.

### Week 1 — Configure and codify (no new code)

1. **Create the `raw / wiki / output / archive` folder layout** under `docs/`. Effort: 30 min. Approval gate: `code-change` (creates folders + READMEs). Stop condition: David rejects the layout name or location.
2. **Codify the comment-tag convention** (`[STATUS]`, `[QUESTION]`, `[APPROVAL-REQUEST]`, `[APPROVAL]`, `[REJECT]`, `[DELIVERABLE]`, `[BLOCKER]`, `[PROMOTION-REQUEST]`, `[ATLAS-NOTE]`, `[ALERT]`) in `docs/atlas/comment-conventions-v0.md`. Effort: 30 min. Approval gate: `code-change`. Stop condition: any conflict with existing Paperclip heartbeat parsing.
3. **Codify the approval-kind taxonomy** in `docs/atlas/approval-policy-v0.md`, with the table from §7.1. Effort: 30 min. Approval gate: `policy-change`.
4. **Add issue templates** (decision request, deep-dive request, build request) as `docs/atlas/templates/*.md` and document the convention for using them. Paperclip doesn't have first-class templates yet; the v1 workaround is "paste from this file." Effort: 1h. Approval gate: `code-change`.

### Week 2 — Install the view layer (new installs)

5. **Install Obsidian-MCP server**, point at `docs/`, configure plugins per §3.4. Effort: 1-2h. Approval gate: `install`. Stop condition: server fails to launch cleanly or Smart Connections embedding fails on initial vault scan.
6. **Install self-hosted Langfuse**, configure OpenRouter / Hermes to emit OTel GenAI spans into it. Effort: 2-4h. Approval gate: `install` + `paid-service` (small infra cost). Stop condition: emit pipeline fails, or storage cost exceeds $X/month after 7 days.

### Week 3 — Build the Daily Operating View (the only custom code)

7. **Write `scripts/render-daily-view.py`** — pulls Paperclip API + repo file mtimes + Langfuse API, renders a single static HTML file at `docs/daily/today.html` (and a markdown variant `today.md` so it lives well in Obsidian). Effort: 4-8h. Approval gate: `code-change`. Stop condition: any of the three data sources is unreliable enough that the view is misleading more than once.
8. **Schedule the script** as a cron / systemd timer to regenerate every 15 min (or on demand via a `make daily-view` target). Effort: 30 min. Approval gate: `code-change`.

### Week 4 — Use, observe, and iterate

9. **Use it for a full week**, with David in David Mode. Atlas in active use. Capture friction in `docs/atlas/runs/<date>-v1-ui-friction-log.md`. No new features built in this week — only observation. Effort: ongoing. Stop condition: a critical flaw emerges that requires a v1.1 ahead of schedule.
10. **End-of-month review** — produce a v1 retrospective memo: what worked, what didn't, what's the v1.1 plan, what (if anything) should become a customer-facing pattern in ClipHub.

### Acceptance criteria for "v1 UI is done"

- David can open the Daily Operating View at the start of a session and answer "what's pending?", "what's blocked?", "what costs am I burning?", "what's stale in my memory?" in under 60 seconds.
- Every approval gesture happens via `[APPROVAL-REQUEST]` / `[APPROVAL]` comments with no inference of approval from agent-turn continuation.
- Every Atlas run emits OTel spans into Langfuse and is reachable via a deep link from its `[STATUS]` comment.
- The repo `docs/` folder layout is in place and respected by every agent run.
- No custom UI code exists outside `scripts/render-daily-view.py` and its template.

### Out of scope for v1 (re-stating, because important)

No custom dashboard. No mobile. No real-time stream. No vector DB. No multi-tenant. No customer UI. No new agents. (See §9 for the full deferred-until table.)
