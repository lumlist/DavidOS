## 1. Revised v1 UI plan

The v1 operating UI is a configured composition of three already-running surfaces plus one thin custom view layer:

1. **Paperclip** — primary control plane (issues, runs, work products, activity, agents, costs).
2. **Obsidian-MCP over `docs/`** — David's read/write cognition surface, gated on install review.
3. **Langfuse (self-hosted)** — observability of every agent run, gated on install review.
4. **Daily Operating View** — a thin, mostly-read-only single-page briefing assembled from Paperclip + repo + Langfuse via APIs. The only custom UI element shipped in v1.

Why this shape — in priority order:
- **Input quality first.** David's #1 friction is that free-form input produces low-signal context. The Daily Operating View pulls from a templated Daily Note (`docs/daily/YYYY-MM-DD.md`) and from Atlas-led intake conversations that produce Decision Memos, both of which structure input before agents act on it. Without this, the rest of the system runs on noisy intent.
- **Observability second.** Every active task, project, agent, and the system itself is legible at a glance. Langfuse provides per-run / per-day / per-agent cost, trace, and tool-call rollups. The Daily Operating View surfaces just three system-health numbers; deep links go to Langfuse.
- **Decisions and approvals third.** `[APPROVAL-REQUEST]` / `[APPROVAL]` comment convention; pending approvals visible in the Daily Operating View; approval is always an explicit, separate gesture.
- **Memory hygiene fourth.** Repo-as-truth (`raw / wiki / output / archive / daily / atlas`); curation gates as folder-permission convention; freshness signals on the Daily Operating View.
- **Stay-out-of-the-way fifth.** No feature ships in v1 unless it directly serves one of the four above.

What does **not** ship in v1: custom dashboard frameworks, real-time agent activity streams, custom chat UI, vector DB over the vault, multi-tenant flows, customer-facing iZZi product UI, custom approval-gate UI, mobile, notifications. Each has a deferred-until trigger documented in the "What not to build yet" table from DAV-16 §9, carried over unchanged.

The Daily Operating View — concrete shape:
- A single static HTML file at `docs/daily/today.html` plus a markdown mirror at `docs/daily/today.md` so it lives in Obsidian.
- Generated by `scripts/render-daily-view.py` on demand and on a 15-minute schedule.
- Sections, in this order on the page (input-quality-first ordering):
  1. **Top of mind** — David-authored, edited in Obsidian (`docs/daily/today.md`). 3-5 bullets max.
  2. **Decisions I want made today** — David-authored from the Daily Note template.
  3. **Pending approvals** — every `[APPROVAL-REQUEST]` without a paired `[APPROVAL]` / `[REJECT]`.
  4. **Open decisions** — every issue labeled `decision-needed`.
  5. **Active issues** — Paperclip board: identifier, project, assignee, status, priority, last activity, "next action."
  6. **Recent deliverables** — last N work-product/document attachments across all issues.
  7. **System health** — three numbers: agent runs in last 24h, total cost in last 24h, heartbeat-loop status (boolean: has any agent issue been reopened from done/cancelled in the last 24h?). Each links to Langfuse / Paperclip detail.
  8. **Memory freshness** — `wiki/` files unedited 60+ days, `raw/` files unpromoted 14+ days, top 10 most-linked `wiki/` hubs.
  9. **Atlas recommendations** — capped at 5 items from `docs/atlas/recommendations-today.md`; Atlas evicts oldest before adding new.

The page is generated, not interactive — all gestures (approve, comment, edit) happen in Paperclip / Obsidian / terminal where they're durably logged.

Surfaces foregrounded in David Mode, in typical order of use:
1. Daily Operating View — start of session.
2. Paperclip board / issue thread — pick up work, comment, assign, approve.
3. Obsidian-MCP over `docs/` — read/write durable memory.
4. Hermes terminal / Atlas chat — strategic conversation.
5. Langfuse trace UI — only when investigating cost or quality anomalies.

Future iZZi customer mode (deferred but designed for): same architecture, parameterized via config keys (`operator_name`, `company_name`, `domains[]`, `approval_gate_strictness`). No David-specific strings hard-coded; every screen, schema, and workflow built for David Mode must be implementable as a parameterized template.
